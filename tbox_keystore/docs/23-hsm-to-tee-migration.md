# TBox 安全芯片 → TEE 迁移项目方案

> 项目汇报材料 | v1.0 | 2026-07-22

---

## 1. 项目背景与迁移动机

### 1.1 当前状态

TBox 车载终端基于 ARM Cortex-A SoC，原方案搭载华大 CIU98B 独立安全芯片，通过 HSM ENGINE + paho 回调机制为 HTTPS 和 MQTTS 提供 TLS 双向认证密钥保护。

### 1.2 迁移目标

将安全锚点从独立安全芯片迁移到 SoC 内置 ARM TrustZone + OP-TEE，消除外部硬件依赖，同时保持应用层接口完全兼容。

### 1.3 痛点与收益

| # | 痛点 | HSM 芯片 | TEE 方案 | 收益 |
|:---:|------|------|------|------|
| 1 | BOM 成本 | $1~3/台 | $0 | 每 10 万台节省 $10~30 万 |
| 2 | 供应链 | 单一厂商依赖 | 纯软件，无硬件绑定 | 零供应风险 |
| 3 | 密钥生命周期 | 出厂烧录固化 | 可生成/导入/删除/轮换 | OTA 可更新 |
| 4 | 容量 | 8 个槽位 | 无限制（100+） | 多业务扩展 |
| 5 | 可审计性 | 黑盒 SDK | 完全开源 | 安全审计 + 国密合规 |
| 6 | 性能 | SPI 总线 ~100ms | SMC 调用 ~50ms | 延迟减半 |
| 7 | 固件升级 | 不支持 | TA OTA 签名更新 | 安全漏洞可修复 |

## 3. 产线灌装流程

### 3.1 灌装时序

```
工厂工控机 (KMS)                          TBox 设备
      │                                      │
      ├─[1] 扫码序列号 ──────────────────────►│ 上电，进入灌装模式
      ├─[2] 验证 HUK 指纹 ◄──────────────────┤ ChipID + HUK Hash
      │                                      │
      ├─[3] 发送灌装 PIN ────────────────────►│ TA: CMD_PIN_INIT
      │                                      │   SHA-256(PIN) 持久化到安全存储
      │                                      │
      ├─[4] 发送密钥生成指令 ─────────────────►│ TA: CMD_KEY_GEN_RSA tls-key
      │                                      │   TA: CMD_KEY_GEN_RSA ota-key
      │                                      │   TA: CMD_KEY_GEN_RSA mqtt-pub-key
      │                                      │   TA: CMD_KEY_GEN_RSA mqtt-sub-key
      │                                      │   密钥在 TEE 内生成，AES-GCM 加密落盘
      │                                      │
      ├─[5] 导出公钥 ◄───────────────────────┤ TA: CMD_KEY_EXPORT_PUB → 各 key 公钥
      │     CSR → CA 签发 → 设备证书 ────────►│
      │     KMS 注册 {序列号, 公钥指纹}        │
      │                                      │
      ├─[6] 发送 Lock ──────────────────────►│ TA: CMD_PROVISION_LOCK
      │                                      │   永久锁定写入，禁止新增/删除密钥
      │                                      │
      └─[7] 断电 ────────────────────────────│ 取走设备
```

### 3.2 灌装安全要点

| 环节 | 安全措施 |
|------|------|
| 通信通道 | 工控机与设备 USB 直连，不接入公网 |
| PIN 保护 | 灌装 PIN 由 KMS 生成，灌装完成后立即废弃 |
| 密钥生成 | TEE 内部 `TEE_GenerateKey`，私钥永不出安全域 |
| 证书签发 | CSR 通过 ENGINE 签名 → Root CA 离线签发 |
| Lock 锁定 | `CMD_PROVISION_LOCK` 后禁止写操作，防运行时注入 |
| 审计 | 每台设备记录 {时间, 序列号, 操作员, 公钥指纹} |

## 4. OTA 升级 — HTTPS 下载软件包

### 4.1 业务流程

```
TBox 设备                                OTA 云端
    │                                       │
    ├─ 周期性检查更新 ──────────────────────►│ GET /ota/check?version=xxx
    │                                       │
    ├─ 收到更新通知                           │
    │                                       │
    ├─ TLS 1.2 双向认证连接 ─────────────────►│
    │  │                                    │
    │  ├─ ClientHello                       │
    │  ├─ ServerHello + Certificate + CertReq│
    │  ├─ Certificate + ClientKeyExchange   │
    │  ├─ CertificateVerify                 │
    │  │   └─ RSA 签名 → ENGINE → TA → m^d mod n
    │  │      私钥在 TEE 内完成签名              │
    │  └─ CCS + Finished                    │
    │                                       │
    ├─ SSL_write(GET /ota/firmware.bin) ────►│
    │                                       │
    ├─ SSL_read 循环 ←─────────────────────┤ firmware.bin (加密)
    │                                       │
    ├─ RSA 验签（软件，公钥已持有）            │ 验证固件签名
    ├─ TA: AES 解密固件                       │ 固件解密在 TEE 内
    │                                       │
    └─ 刷写固件 → 重启                         │
```

### 4.2 TEE 安全保障点

| 步骤 | TEE 操作 | 安全意义 |
|------|------|------|
| TLS 握手 | ENGINE → `CMD_SIGN` / `CMD_RSA_DECRYPT` | 设备身份私钥不出 TEE |
| 固件验签 | 公钥在 REE 侧软件验签 | 公钥可公开，无需 TEE |
| 固件解密 | TA: `CMD_DECRYPT_AES` | 对称密钥在 TEE 内 |

## 5. MQTTS — 控制报文下发与订单数据上传

### 5.1 业务流程

```
TBox 设备                                EMQX Broker (:8883)
    │                                       │
    │    TLS 1.2 双向认证                      │
    ├────────────────────────────────────────│
    │  │  MQTT CONNECT (clientId=tbox-xxxx) │
    │  │  ← 证书验证 (Root CA 签发)           │
    │                                       │
    │  ┌────────── 上行通道 ──────────┐       │
    │  │                              │       │
    │  ├─ PUBLISH topic=order/upload ──────►│ 订单数据上报
    │  │   {orderId, status, gps, ...}      │
    │  │                              │       │
    │  └──────────────────────────────┘       │
    │                                       │
    │  ┌────────── 下行通道 ──────────┐       │
    │  │                              │       │
    │  │         ◄─────── PUBLISH topic=cmd/ctrl│ 远程控制指令
    │  ├─ SUBSCRIBE topic=cmd/ctrl           │ {cmd: "restart", params:...}
    │  │                              │       │
    │  └──────────────────────────────┘       │
    │                                       │
    ├─ PINGREQ ──────────────────────────────│ 心跳保活 (60s)
    │                                       │
    └─ DISCONNECT ──────────────────────────│
```

### 5.2 多密钥隔离

为满足 OP-TEE 3.2 并发限制，MQTTS 发布和订阅使用独立 TA 密钥：

| 通道 | Key Label | 证书 | 权限 |
|------|-----------|------|:---:|
| 上行（数据上报） | `mqtt-pub-key` | mqtt-pub.crt | SIGN |
| 下行（指令接收） | `mqtt-sub-key` | mqtt-sub.crt | SIGN |

每个进程只加载自己的 key，互不冲突。生产环境可进一步部署 `tbox_keyd` 守护进程统一管理会话。

### 5.3 TEE 安全保障点

| 步骤 | TEE 操作 | 安全意义 |
|------|------|------|
| MQTTS CONNECT | ENGINE → `CMD_SIGN` CertificateVerify | 设备认证私钥在 TEE 内 |
| 上行数据 | TLS 通道加密（AES-GCM） | 传输加密在会话层 |
| 下行指令 | TLS 通道 + 应用层可加签 | 防篡改、防重放 |
| 连接保活 | PINGREQ/PINGRESP 在 TLS 通道内 | 防会话劫持 |

## 6. TEE 安全保障全流程

### 6.1 端到端安全链路

```
┌──────────┐    ┌─────────────┐    ┌──────────────┐    ┌───────────────┐
│ 安全启动   │───►│ OP-TEE 加载  │───►│ 密钥操作      │───►│ TLS 会话      │
│ (硬件信任根)│    │ TA 验签     │    │ (TEE 内)     │    │ (端到端加密)  │
└──────────┘    └─────────────┘    └──────────────┘    └───────────────┘
     │               │                    │                    │
     ▼               ▼                    ▼                    ▼
 BootROM →      TA 签名由          m^d mod n           AES-GCM 会话密钥
 SPL →          OP-TEE Core        在 Secure RAM       在 TLS 层协商
 OP-TEE →       验签后加载          中完成              REE 只持有会话密钥
 Linux Kernel                                           私钥永不出 TEE
```

### 6.2 安全纵深防御

| 层级 | 机制 | 防护目标 |
|:---:|------|------|
| L1 硬件 | SoC eFuse HUK + Secure Boot | 启动链防篡改 |
| L2 系统 | OP-TEE OS + TA 签名验证 | 运行时 TA 完整性 |
| L3 存储 | HUK → SSK → TSK → FEK → AES-GCM | 密钥静态加密 |
| L4 访问 | PIN + Lock + key ACL | 操作授权 |
| L5 通信 | TLS 1.2 双向认证 | 传输加密 + 身份认证 |
| L6 运维 | KMS 证书吊销 + 审计日志 | 生命周期管理 |

### 8.3 HSM → TEE 迁移的法规差距矩阵

| 法规维度 | HSM 芯片 (CIU98B) | TEE (OP-TEE) | 差距 | 弥补措施 |
|------|:---:|:---:|:---:|------|
| 密码模块认证 | 国密二级 + CC EAL5+ | 无认证 | **高** | 启动国密 + CC 认证（费用 $15~25 万） |
| 物理防篡改 | 芯片硬件级 | TrustZone 逻辑隔离 | **中** | RPMB + Secure Boot + JTAG 熔断 |
| 安全启动 | SoC 加载 + 芯片独立 | SoC 级信任链 | **低** | Secure Boot 已覆盖 |
| 密钥出口控制 | 设计上禁止 | 设计上禁止 | **无** | 两者等价 |
| 车厂准入资质 | 已列入供应商物料表 | 需重新提交 | **中** | 提前与车厂沟通测试计划 |
| 招标硬件要求 | "独立安全芯片"字样 | 需澄清等效性 | **中** | 提供技术白皮书，说明 TrustZone 等效性 |

### 8.4 风险评估与建议

```
高风险管理:
  ┌─────────────────────────────────────────────────────────────┐
  │ 密码模块认证 (国密 / CC)                                     │
  │   → 尽早启动认证流程，预留 12 月认证周期                      │
  │   → HSM 方案可并行维持，TEE 认证通过后切换                    │
  │                                                             │
  │ 物理防篡改差距                                                │
  │   → 量产使用 RPMB 防回滚 + Secure Boot                       │

  │   → 关键应用场景可保留 HSM + TEE 混合方案 (HSM 存根密钥)      │
  └─────────────────────────────────────────────────────────────┘

中等风险管理:
  ┌─────────────────────────────────────────────────────────────┐
  │ 车厂准入 / 招标合规                                           │
  │   → 提前准备技术白皮书 (TrustZone 等效性论证)                  │
  │   → 与车厂质量/安全部门开技术评审会                            │
```

### 8.5 总结

| | HSM 芯片 | TEE (OP-TEE) | 推荐 |
|------|:---:|:---:|:---:|
| 技术安全 | ★★★★★ | ★★★★ | HSM 略优（物理防护） |
| 法规合规（国内） | ★★★★★ | ★★★ | HSM 优（已有认证） |
| 法规合规（海外） | ★★★★ | ★★★★ | 相近 |
| 成本 / 灵活性 | ★★ | ★★★★★ | TEE 优 |
| **综合** | **认证成熟，物理安全强** | **成本极低，灵活可升级** | — |

**建议**：中长期采用 TEE 方案，同步启动认证流程。短期内 HSM 方案在已认证车型上保留，TEE 在新车型/改版上逐步切换。充电桩场景优先切换 TEE（招标风险低于车载）。
