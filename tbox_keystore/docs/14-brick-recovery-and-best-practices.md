# TEE 设备变砖场景与救砖方案大全

> **背景**：TEE（OP-TEE）设备在产线灌装、生产运行、密钥轮换等阶段可能因操作失误、存储损坏或安全策略触达导致设备无法正常使用（变砖）。本文档全面记录各种变砖场景、恢复手段及行业关注的最佳实践。

---

## 一、什么是 TEE 语境下的"变砖"

在 TEE 设备中，"变砖"不仅仅指设备完全无法启动，而是分层次的概念：

| 级别 | 现象 | 影响范围 |
|------|------|----------|
| **L0 — 完全砖** | BootROM 校验失败，设备无任何响应 | 物理报废 |
| **L1 — 安全启动砖** | Secure Boot 验签失败，系统无法引导 | 无法进入任何系统 |
| **L2 — TEE 数据砖** | TEE 安全存储损坏/锁死，无法执行密钥操作 | 业务功能丧失 |
| **L3 — 应用砖** | TA 被 Lock/密钥丢失，特定业务不可用 | 局部功能丧失 |

本文档重点讨论 **L2/L3 级别**的变砖场景——TEE 安全存储层和 TA 层面的恢复。

## 二、安全存储层回顾

### 2.1 数据加密链

OP-TEE 的安全存储基于从 SoC 硬件唯一密钥（HUK）派生出的层层加密：

```
SoC eFuse (HUK) — 硬件唯一，每芯片不同，REE 不可读
      │
      ▼
SSK = HMAC-SHA256(HUK, ChipID || "OP-TEE Secure Storage")
      │  安全存储密钥，OP-TEE 启动时生成，永存 Secure RAM
      ▼
TSK = HMAC-SHA256(SSK, TA_UUID)
      │  每个 TA 独立，不同 TA 无法解密对方的文件
      ▼
FEK = PRNG() — 每个文件一个随机密钥
      │  用 TSK 加密存储于文件头
      ▼
数据 = AES-GCM-Encrypt(FEK, plaintext)
      │  每文件独立密钥，GCM 认证标签防篡改
      ▼
物理存储:  /data/tee/<N> (REE FS)  或  eMMC RPMB 分区
```

### 2.2 两种存储后端对比

| 特性 | REE FS (`CFG_REE_FS=y`) | RPMB (`CFG_RPMB_FS=y`) |
|------|-------------------------|------------------------|
| 物理位置 | REE 文件系统 `/data/tee/` | eMMC RPMB 安全分区 |
| REE 能否读取 | 可读（但已 AES-GCM 加密，不可解密） | 不可直接访问 |
| REE 能否删除 | ✅ root 可 `rm` | ❌ 需要 RPMB 认证密钥 |
| 防回滚 | ❌ 软件层（hash tree 内部保护） | ✅ 硬件写计数器 |
| 性能 | ★★★★ | ★★（认证写开销） |
| 量产推荐 | 开发/原型 | ✅ 车规级量产 |

## 三、各种救砖/恢复方案

### 3.1 REE FS 后端：覆盖安全分区恢复

#### 原理

REE FS 后端的持久化对象以加密文件形式存在 `/data/tee/`。REE 侧 root 用户虽无法解密内容，但**可以删除文件**。删除后，OP-TEE 检测到空目录会自动重新初始化。

#### 操作步骤

```bash
# 1. 进入恢复模式 (uboot 中断 / 急救 initramfs)
#    前提: Secure Boot 允许启动恢复镜像，或开发板未锁定

# 2. 挂载数据分区
mount -o rw /dev/mmcblk0pX /mnt/data

# 3. 删除所有安全存储文件
rm -rf /mnt/data/tee/*

# 4. 重启
reboot

# 5. OP-TEE 重新初始化 REE FS
#    所有 TA 的持久化对象消失
#    tbox_keystore 回到未灌装状态 (PIN_UNSET)
```

#### 安全分析

```
┌──────────────────────────────────────────────────────────────┐
│ 攻击者能做什么:                                                │
│   • 删除加密文件 → 拒绝服务（密钥丢失）                         │
│   • 不能读密钥明文 (AES-GCM 加密)                              │
│   • 不能篡改密钥 (GCM 认证标签校验会拒绝)                      │
│                                                              │
│ 结论: REE FS 保护机密性和完整性，但不保证可用性                 │
└──────────────────────────────────────────────────────────────┘
```

#### 可行性矩阵

| 环境 | 可删除 REE FS | 可重新灌装 | 救砖可行 |
|------|:---:|:---:|:---:|
| 开发板，无 Secure Boot | ✅ | ✅ | ✅ |
| 开发板，有 Secure Boot，有恢复模式 | ✅ | ✅ | ✅ |
| 生产设备，无 root shell | ❌ | — | ❌ |
| 生产设备，Secure Boot + 关闭调试 | ❌ | — | ❌ |

### 3.2 RPMB 后端：硬件级防护下的恢复

#### 原理

RPMB（Replay Protected Memory Block）是 eMMC 的安全分区，所有写操作需要 HMAC-SHA256 认证，且被硬件写计数器保护。这不是文件系统，REE 无法 mount 或直接操作。

#### 能否擦除 RPMB？

```
┌──────────────────────────────────────────────────────────────┐
│ 途径 1: REE 侧直接擦除                                        │
│   RPMB 不是文件系统 ← 无法 mount/rm                            │
│   结果: ❌ 不可行                                              │
│                                                              │
│ 途径 2: OP-TEE supplicant 转发                                │
│   tee-supplicant 只是 RPMB 请求的转发代理                      │
│   不会允许任意擦除操作                                         │
│   结果: ❌ 不可行                                              │
│                                                              │
│ 途径 3: 开发测试密钥 (CFG_RPMB_TESTKEY=y)                     │
│   开发用固定密钥，安全启动链不校验                              │
│   可通过 OP-TEE 调试接口重置 RPMB                              │
│   结果: ⚠️ 仅开发板可用，量产绝不能                             │
│                                                              │
│ 途径 4: 量产 RPMB 认证密钥                                     │
│   密钥储存在 eFuse / OTP，外部不可读取                         │
│   只有 OP-TEE 内部能发起 RPMB 写入                             │
│   结果: ❌ 无软件擦除路径                                      │
│                                                              │
│ 途径 5: 物理更换 eMMC                                         │
│   HUK 在 SoC eFuse 中，不在 eMMC 上                           │
│   新 eMMC 的 RPMB 是空的                                       │
│   OP-TEE 会重新初始化 RPMB                                    │
│   结果: ⚠️ 硬件维修可行，成本高                                │
│                                                              │
│ 途径 6: SoC 级 HUK 擦除                                       │
│   某些 SoC 支持 JTAG 擦除 eFuse（需 debug 使能位未熔断）        │
│   擦除 HUK → 新的 SSK/TSK → RPMB 数据变成不可解密的噪音        │
│   结果: ⚠️ 需 SoC 厂商支持，量产一般熔断 jtag                   │
└──────────────────────────────────────────────────────────────┘
```

#### 结论

> **RPMB 量产后基本无法在软件层面擦除。这是设计目标——生产设备的密钥集合不可篡改。**

### 3.3 换 TA UUID：开发调试的逃生舱

#### 原理

TSK 与 TA UUID 绑定（`TSK = HMAC-SHA256(SSK, TA_UUID)`），换 UUID → 新命名空间 → 旧数据变成不可解密的噪音，相当于一张白纸。

```
旧 TA: UUID = f8e9209a-3c7d-4d6b-a15e-7f328b11c049
       TSK_old = HMAC-SHA256(SSK, UUID_old)
       /data/tee/* 中旧对象用 TSK_old 派生的 FEK 加密

新 TA: UUID = a1b2c3d4-...              ← 只改这个值，重新编译 TA
       TSK_new = HMAC-SHA256(SSK, UUID_new)
       /data/tee/* 中新对象用 TSK_new 派生的 FEK 加密

旧对象对新 TA 来说 = GCM 认证失败 → 拒绝加载 → 等同于不存在
```

#### 操作步骤

```bash
# 1. 修改 ta/include/tbox_keystore_ta.h 中的 UUID
#define TA_TBOX_KEYSTORE_UUID \
    { 0xa1b2c3d4, ... }          # ← 改这里

# 2. 重新编译 TA，签名，部署
cd ta && make

# 3. 同时更新 CA 和 ENGINE 中的 UUID 引用
#    (如果使用了头文件，只需重新编译即可)

# 4. 部署并重启
#    新 TA 的持久化存储是空白的，可重新灌装
```

#### 代价：存储泄漏

```bash
# REE FS 模式下:
/data/tee/
├── dirf.db       # 包含新旧 TA 所有对象索引
├── 0             # 旧 TA PIN hash     (~128 B)
├── 1             # 旧 TA lock flag     (~128 B)
├── 2             # 旧 TA ota-key       (~3 KB for RSA-2048)
├── 3             # 新 TA PIN hash      (~128 B)  ← 新 TA 可用
├── 4             # 新 TA lock flag      (~128 B)  ← 新 TA 可用
├── 5             # 新 TA ota-key        (~3 KB)   ← 新 TA 可用
...

# 每次换 UUID ≈ 3-5 KB 泄漏
# NAND 上 tee 分区通常几十 MB → 换 100 次也只浪费 ~500 KB
```

#### 可行性

| 环境 | 可行 |
|------|:---:|
| 开发调试 | ✅ |
| 生产（Secure Boot + 无 shell） | ❌ TA 无法部署 |

## 四、恢复能力的分层设计

前面三节的恢复手段是具体操作层面的，本节讨论设计哲学：**如何在保持安全性的前提下提供受控的恢复能力**。

### 4.1 矛盾的本质

安全系统设计中最核心的张力：

```
安全目标 → Lock 后密钥集合不可变 → 误操作无法恢复 → 变砖
运维需求 → 需要有手段重置 Lock → 恢复通道也是攻击面 → 安全被削弱
```

每一个恢复通道都是一条潜在的攻击路径。设计目标不是消除所有恢复能力（那样会让生产事故成本无限大），而是让**授权方**在**可审计**的前提下**有限度**地恢复，同时让**攻击者**走不通这条路。

### 4.2 分层恢复金字塔

把恢复能力按授权难度分级，每级对应不同安全假设：

```
┌──────────────────────────────────────────────────────────────┐
│  恢复层级                    授权方式             攻击面      │
│                                                              │
│  Lv0: 开发逃生             改 UUID / rm tee 文件    无防护    │
│       仅开发板可用          无需授权                          │
│                                                              │
│  Lv1: 产线窗口期恢复        产线安全信道             时间窗口  │
│       设备未出工厂前         工控机签名命令           物理隔离  │
│                                                              │
│  Lv2: 管理员恢复            管理员 PIN               PIN 泄露 │
│       已出厂的设备           单人或多人授权                    │
│                                                              │
│  Lv3: RMA 工厂恢复          HSM 签名授权             物流安全 │
│       设备退回工厂           Debug 证书              物理安全 │
│                                                              │
│  Lv4: 不可恢复              需要 SoC 级擦除          最高安全 │
│       彻底熔断恢复能力       无已知攻击面                      │
└──────────────────────────────────────────────────────────────┘
```

越往下越安全，越往上越灵活。合理的生产策略是组合使用——产线用 Lv1，出厂后保 Lv2，关键设备用 Lv3。

### 4.3 方案 A：双 PIN 分层（推荐，改动最小）

在 tbox_keystore 当前单 PIN 设计上增加 SO PIN（安全管理员 PIN）和 User PIN：

```
当前:
  --init-pin <pin>        ← 单 PIN，既管操作授权又管 Lock 门槛
  --lock                  ← 永久锁，不可逆

改造后:
  --init-so-pin <pin>     ← 安全管理员 PIN（在 User PIN 之前）
  --init-user-pin <pin>   ← 业务操作 PIN
  --lock                  ← 锁定写入操作（禁用 gen/delete）
  --unlock <so-pin>       ← SO PIN 验证后解 User Lock
  --final-lock             ← 终极锁，连 SO unlock 也禁用
                            ↑ 不可逆，只能走 RMA
```

对应的 TA 状态机：

```
UNSET ──init-so-pin──▶ SO_SET ──init-user-pin──▶ READY

READY ──lock──▶ LOCKED ──unlock(so_pin)──▶ READY
                   ▲                            │
                   │                            ▼
                   └──────── 重新 lock ──────────┘

READY ──final-lock──▶ FINAL (不可逆，仅 RMA 可恢复)
LOCKED ──final-lock──▶ FINAL
```

关键安全保证：

| 特性 | 实现方式 |
|------|----------|
| unlock 需要 SO PIN | SO PIN 的 SHA-256 hash 持久化在 TEE 安全存储，unlock 时比对 |
| SO PIN 不出工厂 | 灌装时由工控机生成随机 SO PIN → 注入 TA → 记录到工厂离线 KMS |
| 攻击者不知道 SO PIN | 暴力破解被 TEE 的重试限制阻止（参考 PIN 重试计数器） |
| final-lock 彻底不可逆 | 写一个独立的 `FINAL_LOCK_UUID` 持久化对象，`pin_mgr_restore()` 检测到此对象后永不接受 unlock |
| 审计追踪 | 每次 unlock 在 TA 内递增计数器，下次出厂检测时上报 |

### 4.4 方案 B：物理跳线 + 签名恢复镜像

硬件层面增加恢复路径，安全锚定在物理访问 + 加密签名：

```
┌──────────────────────────────────────────────────────────────┐
│  正常运行:                                                     │
│    GPIO_RECOVERY = LOW                                       │
│    OP-TEE 检查 GPIO → 恢复模式禁用                            │
│    pin_mgr_lock() / final-lock 永久生效                       │
│                                                              │
│  恢复操作（需要物理接触 + HSM 授权）:                           │
│    1. 断开设备电源                                             │
│    2. 打开外壳，短接 RECOVERY 跳线                             │
│    3. 上电 → uboot 检测 GPIO → 加载恢复分区中的恢复镜像         │
│    4. 恢复镜像由工厂 HSM 私钥签名                              │
│    5. OP-TEE 核验签名 → 通过 → 启动恢复 TA                     │
│    6. 恢复 TA 重置 Lock flag、删除指定密钥、允许重新灌装        │
│    7. 完成 → 断开跳线 → 正常启动                               │
│                                                              │
│  安全保证:                                                    │
│    • 物理接触门槛: 远程攻击不可行                              │
│    • HSM 签名: 即使攻击者物理接触到设备，也无法伪造恢复镜像     │
│    • HSM 离线保管于工厂安全房                                  │
│    • 每次 HSM 签名有审计日志 → 可追溯谁、何时、对哪个设备做恢复 │
└──────────────────────────────────────────────────────────────┘
```

### 4.5 方案 C：时间窗口 + 安全计数器

利用 SoC 的安全 RTC 或硬件计数器：

```
产线灌装后 N 小时内 → Lock 可以通过签名 unlock 命令解除
N 小时后 → Lock 自动升级为 FINAL，不可逆

前提条件:
  • SoC 有 Secure RTC（OP-TEE 监控，REE 不可回退）
  • 或使用 RPMB 写计数器模拟时间窗口（每写入一次计数器+1）
  • RTC 断电后由电池或 eFuse 保持

场景适配:
  产线误操作 → N 小时内发现 → 工位旁签名 unlock → 修正 → lock
  出厂后     → 已超时 → 不可恢复 → 走 RMA
```

### 4.6 恢复能力的设计原则

不管选用哪种方案，恢复机制必须遵守以下原则：

| 原则 | 含义 | 反例 |
|------|------|------|
| **授权绑定** | 恢复操作必须绑定可验证的凭证 | 无条件的 unlock 命令 |
| **最小权限** | 恢复凭证只给必需的人/系统 | 所有操作员都能 unlock |
| **范围隔离** | 一次恢复只影响一个设备 | 一个 unlock 密钥解全量设备 |
| **不可抵赖** | 每次恢复有可审计的记录 | 无日志的重置操作 |
| **难度差序** | 恢复比正常操作难一个数量级 | 一键恢复按钮 |
| **物理门槛** | 高安全场景要求物理接触 | 远程 unlock API |
| **时间限界** | 恢复窗口有期限 | 永不过期的恢复能力 |

### 4.7 实际场景对照

```
场景: 产线误锁（忘了生成 ota-key）
  方案 A (SO PIN):     SO 操作员输入 SO PIN → unlock → gen → lock
  方案 B (物理跳线):    短接 RECOVERY 跳线 → 启动签名恢复镜像 → 重置
  方案 C (时间窗口):    N 小时内 → 工控机签名 unlock → 修正 → lock

场景: 设备服役中需要新增业务密钥
  前提: 出厂前未做 final-lock
  方案 A: SO PIN → unlock → gen new-key → lock
  方案 B: 物理接触 + 签名恢复镜像（高安全场景）
  方案 C: 窗口期已过 → 不可行 → 走 RMA 或换设备

场景: 设备退役需要彻底销毁
  所有方案: final-lock → 删除所有持久化对象 → KMS 吊销证书
            → 审计日志记录销毁动作 → CRL/OCSP 生效
```

## 五、生产设备的恢复路径

### 4.1 物理恢复：RMA 流程

量产设备最常见的恢复方式是通过 RMA（Return Merchandise Authorization）返回工厂：

```
┌─────────────────────────────────────────────────────────────┐
│ RMA 恢复流程                                                  │
│                                                              │
│ 1. 设备退回工厂                                               │
│ 2. 通过 JTAG/SWD + 授权 Debug 证书 进入调试模式               │
│ 3. 擦除 RPMB 分区（量产环境下需要 SoC 厂商的授权工具）         │
│ 4. 如果有 Secure Boot: 还需重新烧录完整固件                    │
│ 5. 重新执行产线灌装流程:                                      │
│    ├── --init-pin                                              │
│    ├── --gen-rsa / --gen-aes (各业务密钥)                      │
│    ├── --lock                                                   │
│    └── 更新 KMS 中的设备密钥记录                                │
│ 6. 重新签发设备证书                                            │
│ 7. 功能测试通过 → 退出                                         │
│                                                              │
│ 风险:                                                        │
│   • Debug 证书泄露 → 可解锁任意设备                            │
│   • 物理拆解过程可能损坏硬件                                   │
│   • RMA 耗时 + 物流成本                                       │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 在线恢复：OTA 密钥轮换（不救砖，但防砖）

更好的策略是在 Lock 之前预留 OTA 密钥轮换能力：

```
设计原则:
  1. Lock 前保留至少一个"管理员密钥" (admin-key)
     admin-key 拥有导入新密钥的权限

  2. OTA 流程:
     云端 → 加密的密钥轮换包 → 设备验证签名 → TA CMD_KEY_IMPORT
     （CMD_KEY_IMPORT 需在 Phase 2 实现）

  3. 紧急恢复:
     物理跳线 + 签名过的恢复镜像 → 重置 Lock flag
     （需 Secure Boot 信任链配合）
```

## 六、关键场景与预防措施

### 5.1 产线误锁（没有生成业务密钥就 Lock）

```
场景:
  操作员: --init-pin 123456
  操作员: --lock                    ← 忘记生成密钥！
  结果:   设备变成 L3 砖 — PIN 已锁，零业务密钥，无法回退

预防措施:
  1. Lock 前校验（CA 侧）:
     tbox_keystore --prelock-check   ← 检查必需 label 是否存在

  2. 产线脚本加检查点:
     for key in ota-key tls-key auth-key; do
         tbox_keystore --info "$key" || { echo "$key missing!"; exit 1; }
     done
     tbox_keystore --lock

  3. 双人授权 Lock:
     --lock 需要输入产线管理员 PIN，防止单人误操作
```

### 5.2 密钥意外删除

```
场景:
  运维脚本 bug → tbox_keystore --delete ota-key

当前防护:
  Lock 后 CMD_KEY_DELETE 被拒绝
  未 Lock 时无二次确认

建议:
  --delete 命令增加 -f (force) 和 -i (interactive) 标志
  未 Lock 状态下对关键密钥加确认提示
```

### 5.3 NAND Flash 存储损毁

```
场景:
  NAND 坏块导致 Secure Storage 文件损坏
  GCM 认证标签校验失败 → 密钥永久丢失

防护层级:
  ┌─────────────────────────────────────────────────────────┐
  │ 层级 1: Hash Tree 双版本 (OP-TEE 内置)                    │
  │   每个文件维护 A/B 两个版本，写中断不会破坏数据            │
  │                                                         │
  │ 层级 2: 冗余存储 (业务层)                                 │
  │   关键密钥在多个 TA 中各存一份                            │
  │                                                         │
  │ 层级 3: 外部灾备 (KMS 端)                                 │
  │   产线灌装时 KMS 记录: {序列号 → 密钥指纹, 设备证书}       │
  │   设备丢失后，在 KMS 端吊销对应证书                        │
  │   新设备灌装时注入相同 KMS 记录的密钥（如需密钥恢复）       │
  │                                                         │
  │ 层级 4: 硬件 ECC (eMMC 内置)                              │
  │   eMMC 控制器自带 ECC，可纠正一定数量的 bit 错误           │
  └─────────────────────────────────────────────────────────┘
```

### 5.4 SoC 更换导致 HUK 变化

```
场景:
  设备主板维修 → 更换 SoC → HUK 变化 → 所有旧数据失效
  (HUK 在 SoC eFuse 中，不随 eMMC/NAND 迁移)

影响:
  - /data/tee/* 中所有密文文件变成不可解密
  - 设备密钥全部丢失
  - 设备证书失效（公钥还在，但私钥不可恢复）

恢复路径:
  1. 重新走完整产线灌装流程
  2. KMS 中更新设备证书 (吊销旧证书，签发新证书)
  3. 更新云端设备注册信息 (序列号 → 新公钥 Hash)
```

## 七、行业最佳实践

### 6.1 防砖设计金字塔

```
                    ┌──────────────┐
                    │  硬件恢复     │  ← RMA + JTAG + 授权工具
                    │              │     极少使用，成本最高
                    ├──────────────┤
                    │  在线恢复    │  ← OTA 密钥轮换 + 远程解锁
                    │             │     需要 admin key
                    ├─────────────┤
                    │  防呆机制   │  ← 锁前校验 + 双人授权 + 密钥清单
                    │            │     产线侧预防
                    ├────────────┤
                    │  开发逃生  │  ← 换 UUID + 擦除 REE FS
                    │           │     仅在开发/调试阶段
                    └───────────┘
```

### 6.2 产线灌装的推荐序列

```
1. 设备上电 → 进入灌装模式
2. 工控机验证设备身份 (HUK hash 匹配)
3. TA: --init-pin <PROVISION_PIN>
4. TA: --gen-rsa ota-key   --size 2048 --sign --decrypt
5. TA: --gen-rsa tls-key   --size 2048 --sign --decrypt
6. TA: --gen-aes enc-key   --size 256  --encrypt --decrypt
7. ---- 校验检查点 ----
8. for key in ota-key tls-key enc-key; do
       tbox_keystore --info "$key" || FAIL
   done
9. 导出公钥 → 签发设备证书 → 注册到 KMS
10. ---- 锁定 ----
11. TA: --lock
12. 上报告警: "设备就绪，密钥集合不可变"
```

### 6.3 设备生命周期密钥管理矩阵

| 阶段 | PIN 状态 | Lock 状态 | 可生成密钥 | 可删除密钥 | 可签名 | 可加解密 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| 空白设备 | UNSET | 未锁 | ❌ | ❌ | ❌ | ❌ |
| PIN 已设 | SET | 未锁 | ✅ | ✅ | ✅ | ✅ |
| 灌装完成 | SET | LOCKED | ❌ | ❌ | ✅ | ✅ |
| 设备服役 | SET | LOCKED | ❌ | ❌ | ✅ | ✅ |
| 设备退役 | SET | LOCKED | ❌ | ❌ | ❌¹ | ❌¹ |

> ¹ 退役后 KMS 吊销设备证书，物理销毁设备或擦除安全存储

### 6.4 Debug 授权 vs 生产安全

```
开发/调试:
  CFG_RPMB_TESTKEY=y       ← 允许 RPMB 测试密钥
  CFG_REE_FS=y             ← 允许 REE FS
  JTAG/SWD = 启用
  Secure Boot = 可关闭

生产:
  CFG_RPMB_TESTKEY=n       ← 必须使用烧录到 eFuse 的量产 RPMB 密钥
  CFG_REE_FS=n             ← 禁用 REE FS，只使用 RPMB
  CFG_RPMB_FS=y            ← 启用 RPMB
  JTAG/SWD = 熔断禁用
  Debug 授权 = 仅限 RMA
  Secure Boot = 强制开启

过渡方案 (推荐):
  CFG_REE_FS=y + CFG_RPMB_FS=y  (混合模式)
  → REE FS 数据 + RPMB 存 dirf.db 哈希做完整性校验
  → 性能接近 REE FS，安全接近 RPMB
```

### 6.5 密钥备份策略对比

| 策略 | 描述 | 安全风险 | 适用场景 |
|------|------|----------|----------|
| **不备份** | 私钥永不离开 TEE | 无 | 车规级，一机一密 |
| **KMS 记录公钥** | KMS 存储 `{序列号 → 公钥 Hash}` | 低（仅公钥信息） | 证书签发 + 吊销 |
| **KMS 生成并注入** | KMS 生成密钥 → 通过安全通道注入 TA | 中（KMS 端泄露风险） | 同型号密钥一致性要求 |
| **HSM 备份** | 在离线 HSM 中保存密钥加密副本 | 低（HSM 物理安全） | 高可用要求 |
| **分片备份** | Shamir 密钥分片，多地点存储 | 最低 | 国家级安全需求 |

## 八、法律法规与合规

### 7.1 数据保护法规

| 法规 | 密钥数据 | 影响 |
|------|----------|------|
| **GDPR** | 个人数据加密密钥 | 设备退役时需证明密钥已销毁 |
| **CCPA** | 加州消费者隐私 | 同上 |
| **国密** | 商用密码产品 | 密钥全生命周期管理需通过认证 |
| **WP.29 (UN R155/R156)** | 车联网安全 | 要求 OTA 更新、安全事件响应 |
| **ISO 21434** | 道路车辆网络安全 | 密钥管理需落实威胁分析/TARA |

### 7.2 设备退役的密钥销毁证明

```
销毁动作:
  1. TEE 侧: 删除所有持久化对象 (cmd_delete_all, 需新增)
  2. 存储侧: REE FS 擦除 / RPMB 重置
  3. 证书侧: KMS 吊销设备证书
  4. 云端侧: 更新设备注册状态为 "已退役"

销毁证明:
  • "RPMB write counter 从 N 增加到 N+1" → 证明一次写入发生
  • KMS 吊销证书的 CRL/OCSP 记录
  • 审计日志 (谁、何时、为什么销毁)
```

## 九、总结表

| 变砖场景 | 存储后端 | 恢复难度 | 推荐方案 |
|----------|:---:|:---:|------|
| 误锁（忘生成密钥） | REE FS | ★★ | 产线锁前校验 + CA 防呆 |
| 误锁（忘生成密钥） | RPMB | ★★★★★ | 同 REE FS，但无逃生路径 |
| 密钥损坏/丢失 | REE FS | ★★★ | KMS 公钥记录 + RMA |
| 密钥损坏/丢失 | RPMB | ★★★★★ | KMS 公钥记录 + 硬件 RMA |
| SoC 更换 | 任意 | ★★★★ | 重新产线灌装 |
| eMMC/NAND 物理损坏 | 任意 | ★★★★★ | 硬件更换 + 重新灌装 |
| 开发调试卡死 | REE FS | ★ | `rm -rf /data/tee/*` 或改 UUID |
| 开发调试卡死 | RPMB | ★★★ | `CFG_RPMB_TESTKEY=y` + 重置工具 |
